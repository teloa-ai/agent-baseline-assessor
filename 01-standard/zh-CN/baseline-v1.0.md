# 企业智能体身份与授权安全基线

作者：Max · 2026-10-07

本基线以 [CC BY 4.0](../../LICENSE-DOCS) 许可发布。

## 前言

本基线规定企业环境中的智能体在身份与授权上应满足的安全要求。要求先按一次智能体行为的发生顺序、再按跨会话的对象分为十章，每条可单独验证，并分为 L1 至 L3 三级。

贯穿全部要求的总纲是最小自主（least agency），只给 Agent 完成业务所需的最小行动范围和自主程度。最小权限管 Agent 能碰什么；最小自主还要管它能自己决定什么，以及在无人值守时能做多久。

本基线有三种用法。

- 平台建设：选定目标等级，逐条实现，要求同时作为设计输入和测试用例。
- 供应商评估：把要求作为问卷，请供应商逐条说明实现方式并提供证据。
- 安全评审：按适用条件筛出相关要求，逐条核对，结论记在配套的评估表里。

当前版本为 v1.0，体例参照 OWASP ASVS 5.0，要求编号格式为「V章.节.条」，如 V4.2.1。引用时请注明版本号。

## 1、范围

本基线适用于在企业内部署或采购的智能体平台与 Harness，只管 Agent 以谁的身份、在什么授权下、通过什么路径访问和产出了什么。执行隔离、出口控制和输出控制是落实授权的执行手段，一并纳入本基线。

适用对象：

- 自建的智能体平台和 Agent 应用
- 采购的 SaaS 智能体平台，以及嵌入在 SaaS 产品中的 Agent
- 在员工终端上运行的 Agent，如编码 Agent、桌面助手、浏览器插件
- 私有化部署和 SaaS 两种交付方式

不在范围内：

- 模型训练和微调的数据治理、模型鲁棒性、对抗样本，参见 OWASP AISVS 和 CSA AICM
- 内容安全和输出准确性，如幻觉、偏见、有害内容
- 下游业务系统自身的访问控制设计；本基线只要求它们能接收并校验代表用户访问时传递的用户身份
- 主机加固、网络边界、漏洞管理等通用基础设施安全，按企业既有基线执行

要求以平台为主语书写。采购场景下，由使用企业按要求核验供应商；要求中的「企业」指使用方，「平台」指提供 Agent 能力的系统，「提供方」指平台的开发或运营方。

## 3、术语和定义

下列术语在本基线中有特定含义，要求中出现时按此理解。

| 编号 | 术语 | 定义 |
| --- | --- | --- |
| 3.1 | 智能体（Agent） | 能理解目标、调用工具、自主完成多步任务的 AI 系统。本基线正文简称 Agent |
| 3.2 | Harness | 包在模型外面、让 Agent 能感知和行动的软件层，由多个子系统组成：Agent 循环、上下文管理（含压缩）、工具层、安全控制（权限、审批、钩子）、编排（规划、子 Agent）、扩展接口（Skill、插件、MCP）。Claude Code、Claude Agent SDK、DeepAgents 属于此类。本基线保留英文原词 |
| 3.3 | 框架（Framework） | 提供模型调用、工具定义等开发抽象的库，如 LangChain、OpenAI Agents SDK、Vercel AI SDK |
| 3.4 | 运行时（Runtime） | 为 Agent 提供持久化执行、状态保存和崩溃恢复的基础设施，如 LangGraph、Temporal。Harness 可以建在运行时之上 |
| 3.5 | 执行环境 | Harness 执行代码、命令、文件和浏览器操作的环境，如容器沙箱、虚拟机、员工终端 |
| 3.6 | 平台 | 提供 Agent 创建、运行和管理能力的整体系统，包含 Harness、运行时、执行环境、策略决策点、出口网关和管理面 |
| 3.7 | 提供方 | 平台的开发或运营方 |
| 3.8 | 用户 | 在企业 IdP 中有身份、使用 Agent 的自然人 |
| 3.9 | 自主 Agent（autonomous agent） | 以自身身份执行操作、不代表某个用户行事的 Agent，通常以应用身份访问下游，与代表用户访问相对。此处「自主」指以自身身份运行（对应 Microsoft Entra Agent ID 的 autonomous agent），与 3.29 所说的自主程度无关 |
| 3.10 | 委托 | 一个主体把自己的部分权限交给另一个主体代为行使 |
| 3.11 | 代表用户访问（on-behalf-of，OBO） | Agent 以发起用户的授权访问下游，下游按该用户的权限作出授权判定；采用委托语义时，令牌同时标识用户（主体）和 Agent（act 声明中的行为者） |
| 3.12 | 委托链 | 从发起用户或触发源到当前执行者之间逐级委托关系的有序记录，对应 RFC 8693 中嵌套的 act 声明 |
| 3.13 | Agent 授权范围 | 管理员为某个 Agent 配置的可用工具、连接和数据的上限 |
| 3.14 | 有效权限 | 一次调用实际可用的权限。代表用户访问时，取发起用户当前权限、Agent 授权范围和任务声明范围（如有）的交集；自主 Agent 取其自身授权与 Agent 授权范围的交集；子 Agent 和下游 Agent 还要与上游的委托范围取交集 |
| 3.15 | 离线委托任务 | 用户创建后在其不在场时运行的定时任务或长时任务，以及以该用户身份执行的事件触发规则 |
| 3.16 | 策略决策点（policy decision point，PDP） | 根据身份、委托链、操作和上下文作出授权决定的组件 |
| 3.17 | 出口网关（egress gateway） | Agent 访问执行环境之外任何系统（包括企业内部系统和外部服务）的唯一出口，负责执行授权决定、注入凭证和限流，是主要的策略执行点 |
| 3.18 | 工作负载身份（workload identity） | 平台为执行实例签发的可验证身份，由工作负载标识（如 SPIFFE ID）和身份凭证（如 X.509-SVID、JWT-SVID）组成。本基线要求按会话签发并与执行实例绑定，会话对应的用户和 Agent 由平台在签发时登记，网关凭该身份查得 |
| 3.19 | 凭证托管 | 访问下游所需的令牌和密钥由平台保管，只在网关出口注入请求，Agent 与模型均不接触明文 |
| 3.20 | 占位凭证（placeholder credential） | 执行环境和上下文中代替真实凭证的无效值。网关在出口核对目标后将其替换为真实凭证，这一过程称为凭证注入（credential injection） |
| 3.21 | 不可信内容 | 非平台策略和非用户本人输入的内容，包括网页、邮件、文件、工具返回、其他 Agent 的输出 |
| 3.22 | 渠道（交互渠道） | 用户与 Agent 交互的入口，如 Web、IM、邮件、IDE、API |
| 3.23 | 产出物 | Agent 生成并保存或共享的报告、文档、代码等 |
| 3.24 | 记忆 | 跨会话保留并可被后续检索的内容，包括个人记忆和共享知识 |
| 3.25 | 持久化操作 | 使 Agent 在当前会话结束后仍能继续行动的操作，如创建定时任务、触发规则、转发规则、Skill |
| 3.26 | 高风险操作 | 按 V3.1 判定为需要审批或二次认证的操作 |
| 3.27 | 工作空间 | 平台内隔离数据、知识、凭证和 Agent 的管理单元，如租户、部门、项目。与 IDE 中打开的工作区（本基线称项目目录）不同 |
| 3.28 | 负责人 | 对某个 Agent 的配置、权限和行为负责的具名自然人 |
| 3.29 | 最小自主（least agency） | 只给 Agent 完成业务所需的最小行动范围和自主程度，出自 OWASP Top 10 for Agentic Applications for 2026 |
| 3.30 | 非公开数据 | 按企业数据分类分级标准属于非公开级别的数据，具体级别以企业标准为准，对应 lethal trifecta 中的 private data |
| 3.31 | 外发 | 把数据发往企业控制范围之外，即未登记为企业下游系统（见 V4.2.5）的接收方，如外部邮箱、外部网站和外部存储 |
| 3.32 | 任务 | 用户或触发源交给 Agent 的一次工作，从开始到完成或中止，可包含多次模型调用和工具调用 |
| 3.33 | 策略执行点（policy enforcement point，PEP） | 按策略决策点的决定放行或拒绝请求的组件，本基线中由 Harness 的前置检查和出口网关承担 |
| 3.34 | 二次认证（step-up authentication） | 用户已登录后，在执行高风险操作前按更高的认证强度或更近的认证时间重新认证，参见 RFC 9470 |
| 3.35 | 外部主体 | 经身份联邦接入、不在企业 IdP 中的客户或合作伙伴身份 |
| 3.36 | 影子 Agent（shadow AI agent） | 未经登记纳管、由员工自行接入企业资源的 Agent |
| 3.37 | 紧急访问账号（break-glass account） | 企业 IdP 不可用时用于登录管理面的预置账号 |

## 4、参考架构与信任边界

Agent 由模型和 Harness 组成。平台在 Harness 之外再加上身份层、策略决策点、出口网关、数据层、管理面和审计，本基线的每条要求都落在其中一个组件上。

### 4.1 技术栈分层

&#91;embedded content: Agent 技术栈分层 · 模型、Harness、框架、运行时、执行环境\]

Harness 可以借助框架开发，也可以直接运行在运行时上。按 LangChain 的分类（见第 2 章），Claude Code 和 Claude Agent SDK 属于 Harness，LangGraph 属于运行时，LangChain 属于框架。Harness 的安全控制子系统是 V3、V5 多数要求的落点。

### 4.2 平台参考架构

&#91;embedded content: 平台参考架构 · 可信组件与不可信部分\]

模型的输出只是请求，执行环境可能被攻陷，下游返回的内容按不可信处理。所有对外访问只能经过出口网关，真实凭证只在网关注入。

| 组件 | 职责 | 信任假设 | 主要章节 |
| --- | --- | --- | --- |
| 身份层 | 企业 IdP、目录、SCIM，签发用户、Agent 和工作负载身份 | 可信 | V1 |
| 交互渠道 | Web、IM、邮件、IDE、API 等入口，负责身份映射和输出的可见范围 | 可信；经渠道进入的内容不可信 | V1.2、V7 |
| Harness | Agent 循环、上下文管理、工具层、安全控制、编排、扩展接口 | 平台托管时可信；在员工终端运行时不可信，按 V5.4 | V3、V5、V6 |
| 模型 | 生成文本和工具调用请求 | 不可信，输出只是请求 | V3、V6 |
| 策略决策点 | 计算有效权限、判定风险等级、决定是否审批 | 可信 | V2、V3 |
| 出口网关 | 统一出口，注入凭证、校验目标、限流、吊销 | 可信 | V4 |
| 下游系统 | 被访问的 SaaS、内部 API、MCP Server、数据库 | 自行作出授权判定；返回内容不可信 | V4 |
| 数据层 | 知识库、RAG、记忆、产出物 | 可信；存储的内容可能被污染，按不可信内容处理 | V8 |
| 执行环境 | 执行代码、命令、文件和浏览器操作 | 不可信，可能被攻陷 | V5 |
| 管理面 | Agent 登记、连接器、托管策略、生命周期 | 可信 | V9 |
| 审计 | 记录、调阅、导出与留存，以及检测与响应 | 可信 | V10 |

表中组件按图的顺序排列。身份层为其余组件提供身份，排在最前；其后按一次请求经过的先后排列，到下游系统为止；再是 Harness 调用的数据层和执行环境；最后是贯穿全程的管理面和审计。

## 5、威胁模型

本基线假设模型输出不可信、Agent 可能被诱导或攻陷，而企业 IdP 和出口网关可信。全部要求都是为了在这组假设下守住 16 类威胁。

### 5.1 前提假设

- A1：企业 IdP、目录及其签发的身份断言可信。
- A2：策略决策点、出口网关和审计存储可信，其自身的运维受 V9、V10 约束。
- A3：模型输出不可信。模型给出的身份、风险判断、摘要和工具参数，都只是待检查的请求。
- A4：进入上下文的不可信内容可能包含恶意指令。
- A5：下游系统会按收到的身份正确作出授权判定；做不到的下游按 V4.4 处理。
- A6：员工终端不一定受控，端侧运行的 Agent 按 V5.4 处理。

### 5.2 威胁主体

| 编号 | 主体 | 能力 | 典型目标 |
| --- | --- | --- | --- |
| TA1 | 外部攻击者 | 能在网页、邮件、文档、工单、工具返回中放入内容，不直接接触平台 | 借 Agent 的权限外传数据或执行操作 |
| TA2 | 越权的内部用户 | 持有合法账号，权限有限 | 借 Agent、共享会话、群聊或记忆拿到超出自身权限的数据 |
| TA3 | 失控或被攻陷的 Agent | 目标已被注入改写，或其执行环境已被攻陷 | 冒用身份、扩大权限、留下持久化、横向调用其他 Agent |
| TA4 | 恶意供应链组件 | 以第三方 Skill、插件、MCP Server 或项目配置（如代码仓库中的 MCP 定义和钩子）的形式进入平台 | 获得执行权、窃取凭证、植入长期指令 |
| TA5 | 平台内部人员与提供方 | 管理员、运维和提供方支持人员 | 读取凭证库、对话和审计，经运维通道访问客户数据 |
| TA6 | 渠道冒用者 | 外部访客，或被盗的 IM、邮箱账号 | 以员工身份调用 Agent |

## 6、等级与使用方法

要求先按一次 Agent 行为的发生顺序、再按跨会话的对象分章，分为 L1 至 L3 三级，高等级包含低等级的全部要求。

### 6.1 主轴

第 7 至 16 章即 V1 至 V10。前七章沿一次行为的发生顺序排列；后三章按跨会话持续存在的对象组织，分别是数据、Agent 和审计，贯穿全周期。每条要求只归入一章，针对单次行为的要求按它生效的环节归章，针对这三类对象本身的要求归入后三章。

| 阶段 | 章 | 回答的问题 |
| --- | --- | --- |
| 行为之前 | V1 身份与认证 | 谁在发起，哪个 Agent 在执行 |
| 行为之前 | V2 委托与有效权限 | 代表谁，权限上限是多少 |
| 行为之前 | V3 授权决策 | 这一次操作能不能做，要不要人确认 |
| 行为之中 | V4 凭证与出口执行 | 请求怎么出去，凭证怎么注入 |
| 行为之中 | V5 执行隔离 | 代码、命令、浏览器和扩展在什么边界内运行 |
| 行为之中 | V6 上下文与不可信输入 | 读进来的内容能不能影响决策 |
| 行为之后 | V7 输出与可见性 | 结果给谁看，会不会外泄 |
| 全周期 | V8 数据、记忆与产出物 | 数据怎么检索、沉淀和留存 |
| 全周期 | V9 生命周期与治理 | 谁管 Agent，从登记到下线 |
| 全周期 | V10 审计、检测与响应 | 怎么记录、发现和止损 |

### 6.2 等级

| 等级 | 定位 | 适合的平台 |
| --- | --- | --- |
| L1 | 底线。缺失会直接造成越权、凭证泄露或无法追责 | 任何在企业内使用的智能体平台 |
| L2 | 标准。主流企业安全评审会要求的能力 | 处理内部数据、接入多个业务系统的平台 |
| L3 | 增强。纵深防御和精细治理 | 金融、医疗、关键基础设施等高监管行业，或处理高敏感数据的平台 |

判定规则：满足下列任一项的归入 L1。一是缺失时，外部攻击者、越权的内部用户或渠道冒用者（TA1、TA2、TA6）无需其他条件即可越权或取得凭证；二是缺失时，失控的 Agent、恶意供应链组件或平台内部人员（TA3、TA4、TA5）可直接取得凭证明文，或跨用户、跨租户的数据；三是缺失时无法确定一次操作的发起用户、执行 Agent、委托链和审批人。需要组合其他条件才能利用，或主要用于缩小影响面的，归入 L2；面向特定高风险场景或需要较大投入的，归入 L3。L1 要求不以 L2、L3 要求为实现前提。

本版共 240 条要求，分布在 62 个小节：L1 90 条，L2 在此基础上增加 137 条，L3 再增加 13 条。L1 只保留缺失即可被直接利用、或导致无法追责的控制；与其他 L1 要求重叠的实现细节、告警、纵深防御和管理流程归入 L2。

### 6.3 适用条件

部分小节只在平台具备某项能力时适用，小节开头会写明，例如「本节适用于支持离线委托任务的平台」。平台不具备该能力时，整节记为「不适用」，不计入满足率。

### 6.4 规范用语与编号

- 要求一律用「应」书写，是否必须满足由等级和适用条件决定；说明文字中的「宜」不构成要求。
- 编号格式为「V章.节.条」，如 V4.1.3。条目删除后编号不复用，新增条目追加在小节末尾。
- 每条要求描述一个可验证的结果；一条要求含多个分句时，全部满足才判为满足。
- 要求写作「应能」「应支持」的，判定平台具备该能力且可由企业启用；其余要求判定在被评估的部署中已启用并生效。供应商评估只判定前者，安全评审两者都判定。
- 要求约束平台以外的系统（如下游系统、内网服务、员工终端）时，由使用企业负责落实，评估时单独记录责任方。
- 要求中没有给出数值的时限、周期和阈值（如「短有效期」「定期」「约定时长」），判定为企业或平台已书面规定具体数值并在配置中生效。下表是推荐的默认值，企业可按风险调整。

| 项目 | 相关要求 | 推荐默认值 |
| --- | --- | --- |
| 下游访问令牌的有效期 | V1.3.4、V4.6.1 | 不超过 1 小时 |
| 用户禁用或降权后相关调用被拒的时限 | V10.4.1 | 不超过 5 分钟 |
| Agent 连接和权限的复核周期 | V9.4.2 | 每季度一次 |
| 视为长期未使用的期限 | V9.4.3 | 连续 90 天无调用 |

## 9、V3 授权决策

每一次工具调用在执行前都要经过平台的策略检查。能不能做、要不要人确认，由平台按工具和参数判定，模型说的不算。

## 10、V4 凭证与出口执行

出口网关是 Agent 访问下游系统和互联网的唯一通道，真实凭证只在这里注入。没有绕开网关的路径，凭证也只发往它被授权的目标，「不漏」才有保证。
