# 엔터프라이즈 에이전트 신원 및 인가 보안 기준선

Oct 7, 2026 · @MaxL

## 서문

이 기준선은 기업 환경에서 에이전트가 신원과 인가 측면에서 충족해야 하는 보안 요구사항을 규정합니다. 요구사항은 에이전트 한 번의 행위가 발생하는 순서에 따라, 그다음 세션을 넘나드는 대상에 따라 열 개의 장으로 나뉘며, 각 요구사항은 개별적으로 검증할 수 있고 L1에서 L3까지 세 등급으로 구분됩니다.

전체 요구사항을 관통하는 총강은 최소 자율성(least agency)입니다. 에이전트가 업무 수행에 필요한 최소한의 행동 범위와 자율 수준만 부여받아야 합니다. 최소 권한은 에이전트가 무엇을 건드릴 수 있는지를 관리하고, 최소 자율성은 에이전트가 스스로 무엇을 결정할 수 있는지, 그리고 무인 상태에서 얼마나 오래 동작할 수 있는지까지 관리합니다.

본 기준선은 세 가지 방식으로 사용할 수 있습니다.

- 플랫폼 구축: 목표 등급을 정하고 요구사항을 하나씩 구현합니다. 요구사항은 설계 입력이자 시험 사례로도 사용해야 합니다.
- 공급업체 평가: 요구사항을 설문으로 활용하여, 공급업체가 요구사항별 구현 방식을 설명하고 증거를 제출하도록 합니다.
- 보안 검토: 적용 조건에 따라 관련 요구사항을 선별하여 항목별로 확인하고, 결론은 부속 평가표에 기록합니다.

현재 버전은 v1.0이며, 체재는 OWASP ASVS 5.0을 참조합니다. 요구사항 번호는 「장.절.조」 형식(예: V4.2.1)을 따릅니다. 인용할 때는 버전 번호를 함께 표기하십시오.

## 1. 범위

본 기준선은 기업 내부에 배포하거나 조달하는 에이전트 플랫폼과 Harness에 적용됩니다. 에이전트가 누구의 신원으로, 어떤 인가 하에, 어떤 경로로 접근하고 무엇을 산출하는지를 규율합니다. 실행 격리, 출구 통제, 출력 통제는 인가를 이행하는 실행 수단이므로 본 기준선에 함께 포함합니다.

적용 대상은 다음과 같습니다.

- 자체 구축한 에이전트 플랫폼 및 에이전트 애플리케이션
- 조달한 SaaS 에이전트 플랫폼, 그리고 SaaS 제품에 내장된 에이전트
- 직원 단말에서 실행되는 에이전트(코딩 에이전트, 데스크톱 어시스턴트, 브라우저 플러그인 등)
- 사설 배포와 SaaS 두 가지 제공 방식

적용 범위에서 제외되는 항목은 다음과 같습니다.

- 모델 학습 및 미세조정의 데이터 거버넌스, 모델 견고성, 적대적 예제: OWASP AISVS 및 CSA AICM을 참조하십시오.
- 콘텐츠 안전과 출력 정확성(환각, 편향, 유해 콘텐츠 등)
- 하위 업무 시스템 자체의 접근 통제 설계. 본 기준선은 이들 시스템이 사용자를 대리하여 접근할 때 전달되는 사용자 신원을 수신하고 검증할 수 있을 것만 요구합니다.
- 호스트 강화, 네트워크 경계, 취약점 관리 등 범용 기반 인프라 보안: 기업의 기존 기준선에 따릅니다.

요구사항의 주어는 플랫폼입니다. 조달 상황에서는 사용 기업이 요구사항에 따라 공급업체를 검증합니다. 요구사항의 「기업」은 사용 측을, 「플랫폼」은 에이전트 기능을 제공하는 시스템을, 「공급자」는 플랫폼의 개발 또는 운영 주체를 가리킵니다.

## 3. 용어 및 정의

아래 용어는 본 기준선에서 특정한 의미를 가지며, 요구사항에 등장할 때 이 정의에 따라 이해합니다.

| 번호 | 용어 | 정의 |
| --- | --- | --- |
| 3.1 | 에이전트(Agent) | 목표를 이해하고 도구를 호출하며 다단계 작업을 자율적으로 완수하는 AI 시스템. 본 기준선 본문에서는 Agent로 줄여 씁니다. |
| 3.2 | Harness | 모델 바깥을 감싸 에이전트가 인지하고 행동할 수 있게 하는 소프트웨어 계층으로, 여러 서브시스템으로 구성됩니다. 구성 요소는 에이전트 루프, 컨텍스트 관리(압축 포함), 도구 계층, 보안 통제(권한, 승인, 훅), 오케스트레이션(계획, 서브 에이전트), 확장 인터페이스(Skill, 플러그인, MCP)입니다. Claude Code, Claude Agent SDK, DeepAgents가 이 유형에 속합니다. 본 기준선은 영문 원어를 그대로 씁니다. |
| 3.3 | 프레임워크(Framework) | 모델 호출, 도구 정의 등 개발 추상화를 제공하는 라이브러리. 예: LangChain, OpenAI Agents SDK, Vercel AI SDK |
| 3.4 | 런타임(Runtime) | 에이전트에 지속적 실행, 상태 저장, 장애 복구를 제공하는 인프라. 예: LangGraph, Temporal. Harness는 런타임 위에 구축될 수 있습니다. |
| 3.5 | 실행 환경 | Harness가 코드, 명령, 파일, 브라우저 작업을 실행하는 환경. 예: 컨테이너 샌드박스, 가상 머신, 직원 단말 |
| 3.6 | 플랫폼 | 에이전트의 생성, 실행, 관리 기능을 제공하는 전체 시스템. Harness, 런타임, 실행 환경, 정책 결정 지점, 출구 게이트웨이, 관리 평면을 포함합니다. |
| 3.7 | 공급자 | 플랫폼의 개발 또는 운영 주체 |
| 3.8 | 사용자 | 기업 IdP에 신원이 있고 에이전트를 사용하는 자연인 |
| 3.9 | 자율 에이전트(autonomous agent) | 자신의 신원으로 작업을 수행하고 특정 사용자를 대리하지 않는 에이전트. 보통 애플리케이션 신원으로 하위 시스템에 접근하며, 사용자를 대리하는 접근과 대비됩니다. 여기서 「자율」은 자신의 신원으로 동작한다는 뜻(Microsoft Entra Agent ID의 autonomous agent에 대응)이며, 3.29에서 말하는 자율 수준과는 무관합니다. |
| 3.10 | 위임 | 한 주체가 자신의 권한 일부를 다른 주체에게 넘겨 그 주체가 대신 행사하도록 하는 것 |
| 3.11 | 사용자 대리 접근(on-behalf-of, OBO) | 에이전트가 요청 사용자의 인가로 하위 시스템에 접근하고, 하위 시스템은 해당 사용자의 권한에 따라 인가 판단을 내리는 방식. 위임 의미론을 적용할 때 토큰은 사용자(주체)와 에이전트(act 클레임의 행위자)를 동시에 나타냅니다. |
| 3.12 | 위임 체인 | 요청 사용자 또는 트리거 소스에서 현재 실행자까지 단계적으로 이어지는 위임 관계의 순서 있는 기록. RFC 8693에서 중첩된 act 클레임에 대응합니다. |
| 3.13 | 에이전트 인가 범위 | 관리자가 특정 에이전트에 대해 설정한 사용 가능 도구, 연결, 데이터의 상한 |
| 3.14 | 유효 권한 | 한 번의 호출에서 실제로 사용할 수 있는 권한. 사용자를 대리하여 접근할 때는 요청 사용자의 현재 권한, 에이전트 인가 범위, 작업 선언 범위(있는 경우)의 교집합을 취합니다. 자율 에이전트는 자체 인가와 에이전트 인가 범위의 교집합을 취합니다. 서브 에이전트와 다운스트림 에이전트는 상위의 위임 범위와 추가로 교집합을 취합니다. |
| 3.15 | 오프라인 위임 작업 | 사용자가 생성한 후 사용자가 부재한 동안 실행되는 예약 작업 또는 장기 작업, 그리고 해당 사용자의 신원으로 실행되는 이벤트 트리거 규칙 |
| 3.16 | 정책 결정 지점(policy decision point, PDP) | 신원, 위임 체인, 작업, 컨텍스트에 따라 인가 결정을 내리는 컴포넌트 |
| 3.17 | 출구 게이트웨이(egress gateway) | 에이전트가 실행 환경 바깥의 모든 시스템(기업 내부 시스템과 외부 서비스 포함)에 접근하는 유일한 출구. 인가 결정을 집행하고, 자격 증명을 주입하며, 호출량을 제한합니다. 주요 정책 집행 지점입니다. |
| 3.18 | 워크로드 신원(workload identity) | 플랫폼이 실행 인스턴스에 발급하는 검증 가능한 신원. 워크로드 식별자(예: SPIFFE ID)와 신원 자격(예: X.509-SVID, JWT-SVID)으로 구성됩니다. 본 기준선은 세션 단위로 발급하여 실행 인스턴스에 바인딩할 것을 요구하며, 세션에 대응하는 사용자와 에이전트는 플랫폼이 발급 시점에 등록하고 게이트웨이는 이 신원으로 이를 조회합니다. |
| 3.19 | 자격 증명 보관(credential custody) | 하위 시스템 접근에 필요한 토큰과 키를 플랫폼이 보관하고, 게이트웨이 출구에서만 요청에 주입하는 방식. 에이전트와 모델은 평문을 접하지 않습니다. |
| 3.20 | 자리표시자 자격 증명(placeholder credential) | 실행 환경과 컨텍스트에서 실제 자격 증명을 대신하는 무효 값. 게이트웨이는 출구에서 목적지를 확인한 뒤 이를 실제 자격 증명으로 교체하며, 이 과정을 자격 증명 주입(credential injection)이라 합니다. |
| 3.21 | 신뢰할 수 없는 콘텐츠 | 플랫폼 정책도 아니고 사용자 본인의 입력도 아닌 콘텐츠. 웹페이지, 이메일, 파일, 도구 반환값, 다른 에이전트의 출력을 포함합니다. |
| 3.22 | 채널(상호작용 채널) | 사용자가 에이전트와 상호작용하는 진입점. 예: Web, IM, 이메일, IDE, API |
| 3.23 | 산출물 | 에이전트가 생성하여 저장하거나 공유한 보고서, 문서, 코드 등 |
| 3.24 | 메모리 | 세션을 넘어 보존되어 이후 검색될 수 있는 콘텐츠. 개인 메모리와 공유 지식을 포함합니다. |
| 3.25 | 지속성 작업 | 현재 세션이 끝난 뒤에도 에이전트가 계속 행동할 수 있게 하는 작업. 예: 예약 작업 생성, 트리거 규칙, 전달 규칙, Skill |
| 3.26 | 고위험 작업 | V3.1에 따라 승인 또는 단계별(스텝업) 인증이 필요하다고 판정된 작업 |
| 3.27 | 워크스페이스 | 플랫폼 내에서 데이터, 지식, 자격 증명, 에이전트를 격리하는 관리 단위. 예: 테넌트, 부서, 프로젝트. IDE에서 여는 작업 공간(본 기준선에서는 프로젝트 디렉터리라 칭함)과는 다릅니다. |
| 3.28 | 책임자 | 특정 에이전트의 구성, 권한, 행위에 책임을 지는 기명된 자연인 |
| 3.29 | 최소 자율성(least agency) | 에이전트에게 업무 수행에 필요한 최소한의 행동 범위와 자율 수준만 부여하는 원칙. OWASP Top 10 for Agentic Applications for 2026에서 유래합니다. |
| 3.30 | 비공개 데이터 | 기업 데이터 분류 및 등급 기준상 비공개 등급에 속하는 데이터. 구체적 등급은 기업 기준을 따르며, lethal trifecta의 private data에 대응합니다. |
| 3.31 | 외부 전송 | 데이터를 기업 통제 범위 밖으로 내보내는 것. 즉 기업 하위 시스템(V4.2.5 참조)으로 등록되지 않은 수신처로 보내는 것을 말하며, 외부 메일함, 외부 웹사이트, 외부 스토리지가 여기에 해당합니다. |
| 3.32 | 작업 | 사용자 또는 트리거 소스가 에이전트에 맡긴 한 번의 업무. 시작부터 완료 또는 중단까지를 가리키며, 여러 번의 모델 호출과 도구 호출을 포함할 수 있습니다. |
| 3.33 | 정책 집행 지점(policy enforcement point, PEP) | 정책 결정 지점의 결정에 따라 요청을 허용하거나 거부하는 컴포넌트. 본 기준선에서는 Harness의 사전 검사와 출구 게이트웨이가 이를 담당합니다. |
| 3.34 | 단계별 인증(스텝업 인증, step-up authentication) | 사용자가 이미 로그인한 상태에서, 고위험 작업을 실행하기 전에 더 높은 인증 강도 또는 더 최근의 인증 시각으로 다시 인증하는 것. RFC 9470 참조 |
| 3.35 | 외부 주체 | 신원 연합을 통해 접근하며 기업 IdP에 존재하지 않는 고객 또는 협력사의 신원 |
| 3.36 | 섀도 에이전트(shadow AI agent) | 등록 및 관리를 거치지 않고 직원이 임의로 기업 자원에 연결한 에이전트 |
| 3.37 | 비상 접근 계정(break-glass account) | 기업 IdP를 사용할 수 없을 때 관리 평면에 로그인하도록 미리 준비해 둔 계정 |

## 4. 참조 아키텍처 및 신뢰 경계

에이전트는 모델과 Harness로 구성됩니다. 플랫폼은 Harness 바깥에 신원 계층, 정책 결정 지점, 출구 게이트웨이, 데이터 계층, 관리 평면, 감사를 추가로 배치하며, 본 기준선의 모든 요구사항은 이 중 하나의 컴포넌트에 귀속됩니다.

### 4.1 기술 스택 계층

&#91;embedded content: 에이전트 기술 스택 계층 · 모델, Harness, 프레임워크, 런타임, 실행 환경\]

Harness는 프레임워크를 활용하여 개발할 수도 있고, 런타임 위에서 직접 실행될 수도 있습니다. 제2장에서 인용한 LangChain의 분류에 따르면 Claude Code와 Claude Agent SDK는 Harness에, LangGraph는 런타임에, LangChain은 프레임워크에 속합니다. Harness의 보안 통제 하위 시스템은 V3과 V5 요구사항 대부분이 적용되는 지점입니다.

### 4.2 플랫폼 참조 아키텍처

&#91;embedded content: 플랫폼 참조 아키텍처 · 신뢰 가능 컴포넌트와 신뢰할 수 없는 부분\]

모델의 출력은 요청일 뿐이며, 실행 환경은 침해될 수 있고, 하위 시스템이 반환한 콘텐츠는 신뢰할 수 없는 것으로 처리합니다. 모든 외부 접근은 출구 게이트웨이를 거쳐야 하며, 실제 자격 증명은 게이트웨이에서만 주입됩니다.

| 컴포넌트 | 역할 | 신뢰 가정 | 주요 장 |
| --- | --- | --- | --- |
| 신원 계층 | 기업 IdP, 디렉터리, SCIM. 사용자, 에이전트, 워크로드의 신원을 발급 | 신뢰 가능 | V1 |

표의 컴포넌트는 그림의 순서대로 배열합니다. 신원 계층은 나머지 컴포넌트에 신원을 제공하므로 맨 앞에 두었습니다. 그다음은 요청 한 번이 거치는 순서대로 배열하여 하위 시스템까지 이어지며, 이후 Harness가 호출하는 데이터 계층과 실행 환경이 오고, 마지막으로 전 과정을 관통하는 관리 평면과 감사가 놓입니다.

## 5. 위협 모델

본 기준선은 모델 출력을 신뢰할 수 없고, 에이전트가 유도되거나 침해될 수 있으며, 기업 IdP와 출구 게이트웨이는 신뢰할 수 있다고 가정합니다. 모든 요구사항은 이 가정 아래에서 16개 유형의 위협을 막기 위해 마련되었습니다.

### 5.1 전제 가정

- A1: 기업 IdP, 디렉터리 및 이들이 발급한 신원 어서션은 신뢰할 수 있다.
- A2: 정책 결정 지점, 출구 게이트웨이, 감사 저장소는 신뢰할 수 있으며, 이들 자체의 운영은 V9, V10의 제약을 받는다.
- A3: 모델 출력은 신뢰할 수 없다. 모델이 제시하는 신원, 위험 판단, 요약, 도구 파라미터는 모두 검사를 기다리는 요청일 뿐이다.
- A4: 컨텍스트에 들어온 신뢰할 수 없는 콘텐츠에는 악의적인 지시가 포함될 수 있다.
- A5: 하위 시스템은 수신한 신원에 따라 올바르게 인가 판단을 수행한다. 이를 수행하지 못하는 하위 시스템은 V4.4에 따라 처리한다.
- A6: 직원 단말은 통제되지 않을 수 있으며, 단말에서 실행되는 에이전트는 V5.4에 따라 처리한다.

## 6. 등급 및 사용 방법

요구사항은 먼저 에이전트 행위가 발생하는 순서에 따라, 다음으로 세션을 넘나드는 대상에 따라 장으로 나누며, L1에서 L3까지 세 등급으로 구분합니다. 상위 등급은 하위 등급의 모든 요구사항을 포함합니다.

### 6.1 주축

제7장부터 제16장까지, 즉 V1부터 V10까지가 해당합니다. 앞의 일곱 장은 행위가 발생하는 순서를 따르고, 뒤의 세 장은 세션을 넘어 지속되는 대상, 즉 데이터, 에이전트, 감사를 기준으로 구성하며 전 주기에 걸쳐 적용됩니다. 각 요구사항은 한 개의 장에만 귀속됩니다. 단일 행위를 대상으로 하는 요구사항은 그 행위가 효력을 발휘하는 단계에 따라 장을 정하고, 위 세 대상 자체를 대상으로 하는 요구사항은 뒤의 세 장에 넣습니다.

| 단계 | 장 | 답하는 질문 |
| --- | --- | --- |
| 행위 이전 | V1 신원과 인증 | 누가 요청하는가, 어느 에이전트가 실행하는가 |
| 행위 이전 | V2 위임과 유효 권한 | 누구를 대리하는가, 권한 상한은 얼마인가 |
| 행위 이전 | V3 인가 결정 | 이번 작업을 해도 되는가, 사람의 확인이 필요한가 |
| 행위 중 | V4 자격 증명과 출구 실행 | 요청은 어떻게 나가고, 자격 증명은 어떻게 주입되는가 |
| 행위 중 | V5 실행 격리 | 코드, 명령, 브라우저, 확장 기능은 어떤 경계 안에서 실행되는가 |
| 행위 중 | V6 컨텍스트와 신뢰할 수 없는 입력 | 읽어 들인 콘텐츠가 판단에 영향을 줄 수 있는가 |
| 행위 이후 | V7 출력과 가시성 | 결과를 누구에게 보여 주며, 유출될 수 있는가 |
| 전 주기 | V8 데이터, 메모리, 산출물 | 데이터를 어떻게 검색하고, 축적하고, 보존하는가 |
| 전 주기 | V9 수명주기와 거버넌스 | 누가 에이전트를 관리하며, 등록에서 폐기까지 어떻게 하는가 |
| 전 주기 | V10 감사, 탐지, 대응 | 어떻게 기록하고, 발견하고, 피해를 차단하는가 |

### 6.2 등급

| 등급 | 위상 | 적합한 플랫폼 |
| --- | --- | --- |
| L1 | 기본. 결여될 경우 곧바로 권한 초과 접근, 자격 증명 유출 또는 책임 추적 불능이 발생함 | 기업 내에서 사용하는 모든 에이전트 플랫폼 |
| L2 | 표준. 주류 기업 보안 검토에서 요구하는 역량 | 내부 데이터를 처리하고 여러 업무 시스템에 연결하는 플랫폼 |
| L3 | 강화. 심층 방어와 정교한 거버넌스 | 금융, 의료, 중요 인프라 등 고규제 산업, 또는 고민감 데이터를 처리하는 플랫폼 |

판정 규칙은 다음과 같습니다. 아래 중 하나에 해당하면 L1로 분류합니다. 첫째, 결여될 경우 외부 공격자, 권한을 넘어서는 내부 사용자, 채널 사칭자(TA1, TA2, TA6)가 다른 조건 없이 권한을 넘거나 자격 증명을 취득할 수 있는 경우. 둘째, 결여될 경우 통제를 벗어난 에이전트, 악성 공급망 구성 요소, 플랫폼 내부 인력(TA3, TA4, TA5)이 자격 증명 평문이나 사용자 간, 테넌트 간 데이터를 직접 얻을 수 있는 경우. 셋째, 결여될 경우 한 번의 작업에 대한 요청 사용자, 실행 에이전트, 위임 체인, 승인자를 확정할 수 없는 경우. 다른 조건과 결합해야 악용되거나 주로 영향 범위를 축소하는 목적의 통제는 L2로 분류합니다. 특정 고위험 시나리오를 대상으로 하거나 상당한 투자가 필요한 통제는 L3로 분류합니다. L1 요구사항은 L2, L3 요구사항을 구현하는 것을 전제로 하지 않습니다.

본 버전의 요구사항은 총 240건이며 62개 절에 분포합니다. L1은 90건이고, L2는 그 위에 137건을 추가하며, L3는 다시 13건을 추가합니다. L1은 결여 시 곧바로 악용되거나 책임 추적이 불가능해지는 통제만 남겼습니다. 다른 L1 요구사항과 중복되는 구현 세부 사항, 경보, 심층 방어, 관리 절차는 L2로 분류합니다.

### 6.3 적용 조건

일부 절은 플랫폼이 특정 기능을 갖춘 경우에만 적용됩니다. 해당 조건은 절의 시작 부분에 명시하며, 예를 들어 「본 절은 오프라인 위임 작업을 지원하는 플랫폼에 적용된다」와 같이 씁니다. 플랫폼이 해당 기능을 갖추지 않은 경우 절 전체를 「해당 없음」으로 기록하며, 적합률 산정에서 제외합니다.

### 6.4 규범 용어와 번호

- 요구사항은 모두 「~해야 한다」로 서술하며, 필수 충족 여부는 등급과 적용 조건으로 정해집니다. 설명 문장의 「~하는 것이 바람직하다」는 요구사항을 구성하지 않습니다.
- 번호 형식은 「V장.절.조」이며, 예를 들어 V4.1.3과 같습니다. 조항을 삭제해도 번호는 재사용하지 않으며, 신규 조항은 해당 절의 끝에 추가합니다.
- 각 요구사항은 검증 가능한 결과 하나를 서술합니다. 요구사항이 여러 구절로 이루어진 경우 모두 충족되어야 만족으로 판정합니다.
- 「~할 수 있어야 한다」, 「~을 지원해야 한다」로 쓰인 요구사항은 플랫폼이 해당 역량을 갖추고 기업이 이를 활성화할 수 있는 경우 만족으로 판정합니다. 그 밖의 요구사항은 평가 대상 배포에서 활성화되어 효력을 발휘하는 경우 만족으로 판정합니다. 공급업체 평가는 전자만 판정하고, 보안 검토는 두 가지를 모두 판정합니다.
- 요구사항이 플랫폼 밖의 시스템(예: 하위 시스템, 내부망 서비스, 직원 단말)을 규율하는 경우 이행 책임은 사용 기업에 있으며, 평가 시 책임 주체를 별도로 기록합니다.
- 요구사항에 수치가 제시되지 않은 기한, 주기, 임계값(예: 「짧은 유효 기간」, 「정기적으로」, 「약정된 기간」)은 기업 또는 플랫폼이 구체적인 수치를 서면으로 규정하고 설정에 반영한 것으로 판정합니다. 아래 표는 권장 기본값이며, 기업은 위험에 따라 조정할 수 있습니다.

| 항목 | 관련 요구사항 | 권장 기본값 |

## 7. V1 신원과 인증

모든 요청에 대해 두 가지 신원을 확정해야 합니다. 요청하는 사람과 실행하는 에이전트입니다. 두 신원은 모두 플랫폼이 신뢰할 수 있는 출처에서 도출해야 하며, 요청이나 모델이 스스로 주장하는 신원은 채택하지 않습니다.

## 10. V4 자격 증명과 출구 실행

출구 게이트웨이는 에이전트가 하위 시스템과 인터넷에 접근하는 유일한 경로이며, 실제 자격 증명은 이곳에서만 주입됩니다. 게이트웨이를 우회하는 경로가 없어야 하고, 자격 증명도 허가된 목적지에만 전달되어야 「유출되지 않는다」는 보장이 성립합니다.

| 번호 | 요구사항 | L1 | L2 | L3 |

| V4.1.7 | 대화와 업로드 파일에 나타난 자격 증명을 식별하고, 이것이 메모리, 산출물 또는 에이전트 구성에 기록되지 않도록 차단해야 한다 |  | ✓ | ✓ |
