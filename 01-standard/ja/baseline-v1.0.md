# エンタープライズエージェントのID・認可セキュリティベースライン

著者：Max · 2026-10-07

## 前書き

本ベースラインは、企業環境におけるエージェントがID及び認可に関して満たすべきセキュリティ要件を定めるものである。要件は、まず1回のエージェント行動の発生順序に従い、次にセッションを横断する対象に従って10の章に分類する。各要件は単独で検証可能であり、L1からL3までの3つのレベルに区分する。

全要件を貫く総則は最小自律性（least agency）である。すなわち、エージェントが業務を遂行するために必要な最小限の行動範囲と自律性のみを付与する。最小権限は、エージェントが何に触れられるかを管理する。最小自律性は、さらにエージェントが自ら決定できる事項、及び無人の状態で動作を継続できる時間をも管理する。

本ベースラインには3通りの利用方法がある。

- プラットフォーム構築：目標レベルを選定し、要件を1件ずつ実装する。要件は設計入力であると同時にテストケースとしても用いること。
- サプライヤー評価：要件を質問票として用い、サプライヤーに各要件の実装方法を説明させ、根拠となる証跡を提出させる。
- セキュリティレビュー：適用条件に従って関連する要件を抽出し、1件ずつ照合する。結論は付属の評価表に記録する。

本版は v1.0 であり、体裁は OWASP ASVS 5.0 を参照している。要件番号の形式は「V章.節.条」（例：V4.2.1）とする。引用する場合は版番号を明記すること。

## 1、範囲

本ベースラインは、企業内に配備又は調達するエージェントプラットフォーム及びハーネスに適用する。対象とするのは、エージェントがどのIDで、どの認可の下で、どの経路を通じてアクセスし、何を生成したかである。実行隔離、出口制御及び出力制御は、認可を実施するための手段であり、本ベースラインに含める。

適用対象：

- 自社構築のエージェントプラットフォーム及びエージェントアプリケーション
- 調達したSaaS型エージェントプラットフォーム、及びSaaS製品に組み込まれたエージェント
- 従業員の端末上で動作するエージェント（コーディングエージェント、デスクトップアシスタント、ブラウザープラグイン等）
- オンプレミス配備とSaaSの2種類の提供形態

適用範囲外：

- モデルの学習及びファインチューニングにおけるデータガバナンス、モデルの頑健性、敵対的サンプル。OWASP AISVS 及び CSA AICM を参照のこと
- コンテンツの安全性及び出力の正確性（ハルシネーション、バイアス、有害コンテンツ等）
- 下流の業務システム自体のアクセス制御設計。本ベースラインは、それらのシステムがユーザーを代表したアクセスの際に伝達されるユーザーIDを受領し検証できることのみを求める
- ホストの強化、ネットワーク境界、脆弱性管理等の汎用インフラストラクチャのセキュリティ。企業の既存ベースラインに従って実施する

要件は、プラットフォームを主語として記述する。調達の場面では、利用企業が要件に基づいてサプライヤーを検証する。要件中の「企業」は利用側を、「プラットフォーム」はエージェント機能を提供するシステムを、「提供者」はプラットフォームの開発又は運用を行う者をそれぞれ指す。

## 3、用語及び定義

以下の用語は、本ベースラインにおいて特定の意味を持つ。要件中に現れる場合は、この定義に従って解釈する。

| 番号 | 用語 | 定義 |
| --- | --- | --- |
| 3.1 | エージェント（Agent） | 目標を理解し、ツールを呼び出し、自律的に多段階のタスクを完遂できるAIシステム。本ベースラインの本文では「エージェント」と記す |
| 3.2 | ハーネス（Harness） | モデルの外側を包み、エージェントが認識と行動を行えるようにするソフトウェア層。エージェントループ、コンテキスト管理（圧縮を含む）、ツール層、セキュリティ制御（権限、承認、フック）、オーケストレーション（計画、サブエージェント）、拡張インターフェース（Skill、プラグイン、MCP）の複数のサブシステムで構成される。Claude Code、Claude Agent SDK、DeepAgents はこの類型に属する。本ベースラインの本文では「ハーネス」と記す |
| 3.3 | フレームワーク（Framework） | モデル呼び出し、ツール定義等の開発抽象を提供するライブラリ。LangChain、OpenAI Agents SDK、Vercel AI SDK など |
| 3.4 | ランタイム（Runtime） | エージェントに永続的な実行、状態保存及びクラッシュ復旧を提供する基盤。LangGraph、Temporal など。ハーネスはランタイムの上に構築されることがある |
| 3.5 | 実行環境 | ハーネスがコード、コマンド、ファイル及びブラウザー操作を実行する環境。コンテナサンドボックス、仮想マシン、従業員端末など |
| 3.6 | プラットフォーム | エージェントの作成、実行及び管理の機能を提供するシステム全体。ハーネス、ランタイム、実行環境、ポリシー決定点、出口ゲートウェイ及び管理面を含む |
| 3.7 | 提供者 | プラットフォームの開発又は運用を行う者 |
| 3.8 | ユーザー | 企業 IdP においてIDを有し、エージェントを使用する自然人 |
| 3.9 | 自律型エージェント（autonomous agent） | 自身のIDで操作を実行し、いずれかのユーザーを代表して行動しないエージェント。通常はアプリケーションIDで下流にアクセスし、ユーザーを代表したアクセスと対をなす。ここでの「自律」は自身のIDで動作することを指す（Microsoft Entra Agent ID の autonomous agent に対応）。3.29 に述べる自律の程度とは無関係である |
| 3.10 | 委任 | ある主体が自己の権限の一部を別の主体に委ね、代わって行使させること |
| 3.11 | ユーザーを代表したアクセス（on-behalf-of、OBO） | エージェントが要求元ユーザーの認可によって下流にアクセスし、下流はそのユーザーの権限に基づいて認可判定を行う。委任の意味論を採用する場合、トークンはユーザー（主体）とエージェント（act クレームにおける行為者）の双方を識別する |
| 3.12 | 委任チェーン | 要求元ユーザー又はトリガー元から現在の実行者までの、段階的な委任関係の順序付けられた記録。RFC 8693 においてネストされた act クレームに対応する |
| 3.13 | エージェント認可範囲 | 管理者がエージェントに対して設定した、利用可能なツール、接続及びデータの上限 |
| 3.14 | 実効権限 | 1回の呼び出しにおいて実際に利用可能な権限。ユーザーを代表したアクセスの場合は、要求元ユーザーの現在の権限、エージェント認可範囲及びタスク宣言範囲（ある場合）の積集合をとる。自律型エージェントは、自身の認可とエージェント認可範囲の積集合をとる。サブエージェント及び下流エージェントは、さらに上流の委任範囲との積集合をとる |
| 3.15 | オフライン委任タスク | ユーザーが作成し、ユーザーの不在時に実行される定期タスク又は長時間タスク、及び当該ユーザーのIDで実行されるイベント駆動ルール |
| 3.16 | ポリシー決定点（policy decision point、PDP） | ID、委任チェーン、操作及びコンテキストに基づいて認可の決定を行うコンポーネント |
| 3.17 | 出口ゲートウェイ（egress gateway） | エージェントが実行環境の外にある任意のシステム（企業内システム及び外部サービスを含む）へアクセスする唯一の出口。認可決定の実施、資格情報の注入及びレート制限を担う主要なポリシー実施点である |
| 3.18 | ワークロードID（workload identity） | プラットフォームが実行インスタンスに対して発行する検証可能なID。ワークロード識別子（SPIFFE ID など）と ID 資格情報（X.509-SVID、JWT-SVID など）で構成される。本ベースラインは、セッション単位で発行し実行インスタンスに紐づけることを求める。セッションに対応するユーザーとエージェントは、発行時にプラットフォームが登録し、ゲートウェイはこのIDに基づいて照会する |
| 3.19 | 資格情報の保管 | 下流へのアクセスに必要なトークン及びシークレットをプラットフォームが保管し、ゲートウェイの出口でのみリクエストに注入する方式。エージェント及びモデルは平文に接触しない |
| 3.20 | プレースホルダー資格情報（placeholder credential） | 実行環境及びコンテキストにおいて、実際の資格情報の代わりに置かれる無効な値。ゲートウェイは出口で送信先を照合した後、これを実際の資格情報に置き換える。この処理を資格情報注入（credential injection）と称する |
| 3.21 | 信頼されないコンテンツ | プラットフォームのポリシー又はユーザー本人の入力ではないコンテンツ。Webページ、メール、ファイル、ツールの返却値、他のエージェントの出力を含む |
| 3.22 | チャネル（対話チャネル） | ユーザーがエージェントと対話する入口。Web、IM、メール、IDE、API など |
| 3.23 | 成果物 | エージェントが生成し、保存又は共有するレポート、文書、コードなど |
| 3.24 | メモリ | セッションを超えて保持され、後続の検索に用いることができる内容。個人メモリ及び共有ナレッジを含む |
| 3.25 | 永続化操作 | セッション終了後もエージェントが行動を継続できるようにする操作。定期タスクの作成、トリガールールの作成、転送ルールの作成、Skill など |
| 3.26 | 高リスク操作 | V3.1 に従い承認又はステップアップ認証が必要と判定された操作 |
| 3.27 | ワークスペース | プラットフォーム内でデータ、ナレッジ、資格情報及びエージェントを隔離する管理単位。テナント、部門、プロジェクトなど。IDE で開かれるワークスペース（本ベースラインではプロジェクトディレクトリと称する）とは異なる |
| 3.28 | 責任者 | 特定のエージェントの設定、権限及び動作について責任を負う、氏名の特定された自然人 |
| 3.29 | 最小自律性（least agency） | エージェントに業務遂行に必要な最小限の行動範囲と自律の程度のみを与えること。OWASP Top 10 for Agentic Applications for 2026 に由来する |
| 3.30 | 非公開データ | 企業のデータ分類・格付け基準において非公開のレベルに属するデータ。具体的なレベルは企業基準による。lethal trifecta における private data に対応する |
| 3.31 | 外部送信 | データを企業の管理範囲外へ送出すること。すなわち、企業下流システムとして登録されていない（V4.2.5 参照）受信先（外部メールアドレス、外部サイト、外部ストレージなど）へ送ることをいう |
| 3.32 | タスク | ユーザー又はトリガー元がエージェントに委ねる1回の作業。開始から完了又は中止までを指し、複数回のモデル呼び出し及びツール呼び出しを含みうる |
| 3.33 | ポリシー実施点（policy enforcement point、PEP） | ポリシー決定点の決定に従い、リクエストを許可又は拒否するコンポーネント。本ベースラインでは、ハーネスの事前チェック及び出口ゲートウェイがこれを担う |
| 3.34 | ステップアップ認証（step-up authentication） | ユーザーがログイン済みの状態で、高リスク操作の実行前に、より高い認証強度又はより新しい認証時刻に基づき再認証すること。RFC 9470 を参照 |
| 3.35 | 外部主体 | ID連携を経て接続される、企業 IdP に存在しない顧客又はパートナーのID |
| 3.36 | シャドーAIエージェント（shadow AI agent） | 登録管理されていないまま、従業員が自ら企業リソースに接続したエージェント |
| 3.37 | 緊急アクセスアカウント（break-glass account） | 企業 IdP が利用できない場合に、管理面へログインするために事前に用意されたアカウント |

## 4、リファレンスアーキテクチャと信頼境界

エージェントはモデルとハーネスで構成される。プラットフォームは、ハーネスの外側にIDレイヤー、ポリシー決定点、出口ゲートウェイ、データ層、管理面及び監査を加える。本ベースラインの各要件は、そのいずれかのコンポーネントに対応する。

### 4.1 技術スタックの階層

&#91;埋め込みコンテンツ：エージェント技術スタックの階層 · モデル、ハーネス、フレームワーク、ランタイム、実行環境\]

ハーネスはフレームワークを用いて開発することもでき、ランタイム上で直接動作させることもできる。LangChain の分類（第2章参照）に従えば、Claude Code 及び Claude Agent SDK はハーネスに、LangGraph はランタイムに、LangChain はフレームワークにそれぞれ属する。ハーネスのセキュリティ制御サブシステムは、V3 及び V5 の要件の大半が適用される対象である。

### 4.2 プラットフォームのリファレンスアーキテクチャ

&#91;埋め込みコンテンツ：プラットフォームのリファレンスアーキテクチャ · 信頼できるコンポーネントと信頼されない部分\]

モデルの出力は要求にすぎず、実行環境は侵害される可能性があり、下流から返されるコンテンツは信頼されないものとして扱う。すべての外部アクセスは出口ゲートウェイを経由するしかなく、実際の資格情報はゲートウェイでのみ注入する。

| コンポーネント | 責務 | 信頼の前提 | 主な章 |
| --- | --- | --- | --- |
| IDレイヤー | 企業 IdP、ディレクトリ、SCIM。ユーザー、エージェント及びワークロードのIDを発行する | 信頼できる | V1 |
| 対話チャネル | Web、IM、メール、IDE、API 等の入口。IDの対応付け及び出力の可視範囲を担う | 信頼できる。チャネル経由で入るコンテンツは信頼されない | V1.2、V7 |
| ハーネス | エージェントループ、コンテキスト管理、ツール層、セキュリティ制御、オーケストレーション、拡張インターフェース | プラットフォームが管理する場合は信頼できる。従業員端末で動作する場合は信頼されず、V5.4 に従う | V3、V5、V6 |
| モデル | テキスト及びツール呼び出しの要求を生成する | 信頼されない。出力は要求にすぎない | V3、V6 |
| ポリシー決定点 | 実効権限を算出し、リスクレベルを判定し、承認の要否を決定する | 信頼できる | V2、V3 |
| 出口ゲートウェイ | 出口を一元化し、資格情報を注入し、送信先を検証し、レート制限及び失効を行う | 信頼できる | V4 |
| 下流システム | アクセスの対象となる SaaS、内部 API、MCP Server、データベース | 独自に認可判定を行う。返却内容は信頼されない | V4 |
| データ層 | ナレッジベース、RAG、メモリ、成果物 | 信頼できる。保存された内容は汚染される可能性があり、信頼されないコンテンツとして扱う | V8 |
| 実行環境 | コード、コマンド、ファイル及びブラウザー操作の実行 | 信頼されない。侵害される可能性がある | V5 |
| 管理面 | エージェントの登録、コネクター、管理ポリシー、ライフサイクル | 信頼できる | V9 |
| 監査 | 記録、閲覧、エクスポート及び保持、並びに検知と対応 | 信頼できる | V10 |

表中のコンポーネントは図の順序に従って並べている。IDレイヤーは他のすべてのコンポーネントにIDを提供するため最前に置く。その後は1回のリクエストが通過する順序に従い、下流システムまでを並べる。続いて、ハーネスが呼び出すデータ層及び実行環境を置き、最後に全体を通じて存在する管理面及び監査を置く。

| 5 | 人による確認 | 実際のパラメータに基づき承認を生成し、必要に応じてステップアップ認証を行う | ハーネス、IDレイヤー | V3.4、V3.5 |

| 10 | 全工程の記録 | 各手順を監査に書き込み、人、エージェント及び入力元まで遡れるようにする | 監査 | V10.1 |

## 5、脅威モデル

本ベースラインは、モデルの出力は信頼されず、エージェントは誘導又は侵害されうる一方、企業 IdP 及び出口ゲートウェイは信頼できると仮定する。全要件は、この前提の下で16類の脅威を防ぐために定められている。

### 5.1 前提条件

- A1：企業 IdP、ディレクトリ及びそれらが発行するID主張は信頼できる。
- A2：ポリシー決定点、出口ゲートウェイ及び監査ストレージは信頼できる。それら自身の運用は V9、V10 の規制を受ける。
- A3：モデルの出力は信頼されない。モデルが示すID、リスク判断、要約及びツールパラメータは、いずれも検査すべき要求にすぎない。
- A4：コンテキストに入った信頼されないコンテンツには、悪意のある指示が含まれている可能性がある。
- A5：下流システムは、受け取ったIDに基づき正しく認可判定を行う。これを行えない下流は V4.4 に従って扱う。
- A6：従業員端末は必ずしも管理下にあるとは限らない。端側で動作するエージェントは V5.4 に従って扱う。

### 5.2 脅威主体

| 番号 | 主体 | 能力 | 典型的な目的 |
| --- | --- | --- | --- |
| TA1 | 外部攻撃者 | Webページ、メール、文書、チケット、ツールの返却値に内容を仕込むことができるが、プラットフォームに直接接触しない | エージェントの権限を借りてデータを外部へ送り出す、又は操作を実行させる |
| TA2 | 権限を逸脱した内部ユーザー | 正当なアカウントを保持するが、権限は限定されている | エージェント、共有セッション、グループチャット又はメモリを借りて、自身の権限を超えるデータを取得する |
| TA3 | 制御を失った又は侵害されたエージェント | 目標が注入によって書き換えられた、又は実行環境が侵害されている | IDを詐称する、権限を拡大する、永続化を残す、他のエージェントを横方向に呼び出す |
| TA4 | 悪意のあるサプライチェーン構成要素 | サードパーティの Skill、プラグイン、MCP Server、又はプロジェクト構成（コードリポジトリ内の MCP 定義及びフックなど）の形でプラットフォームに入り込む | 実行権限の取得、資格情報の窃取、長期的な指示の埋め込み |

| TA6 | チャネルのなりすまし者 | 外部の訪問者、又は窃取された IM 若しくはメールアカウント | 従業員のIDでエージェントを呼び出す |

## 6、レベルと利用方法

要件は、まずエージェントの1回の行動が発生する順序に従い、次にセッションを横断する対象に従って章を分け、L1からL3までの3段階に区分する。上位のレベルは下位のレベルのすべての要件を含む。

### 6.1 主軸

第7章から第16章、すなわち V1 から V10 である。前の7章は1回の行動の発生順序に従って並べ、後の3章はセッションを横断して存続する対象（データ、エージェント及び監査）に従って構成し、全ライフサイクルにわたる。各要件は1つの章にのみ属する。単一の行動を対象とする要件は、それが有効となる段階に従って章に配置し、これら3類の対象そのものを対象とする要件は後の3章に配置する。

| 段階 | 章 | 問い |
| --- | --- | --- |
| 行動の前 | V1 IDと認証 | 誰が開始しているのか、どのエージェントが実行しているのか |
| 行動の前 | V2 委任と実効権限 | 誰を代表しているのか、権限の上限はどこか |
| 行動の前 | V3 認可決定 | この1回の操作を行ってよいか、人による確認が必要か |
| 行動の中 | V4 資格情報と出口での実行 | リクエストはどのように外へ出るのか、資格情報はどのように注入されるのか |
| 行動の中 | V5 実行隔離 | コード、コマンド、ブラウザー及び拡張はどの境界内で動作するのか |
| 行動の中 | V6 コンテキストと信頼されない入力 | 読み込まれたコンテンツが判断に影響してよいか |
| 行動の後 | V7 出力と可視性 | 結果は誰に見せるのか、外部へ漏えいしないか |
| 全周期 | V8 データ、メモリ及び成果物 | データはどのように検索され、蓄積され、保持されるか |
| 全周期 | V9 ライフサイクルとガバナンス | 誰がエージェントを管理するのか、登録から廃止までどのように行うか |
| 全周期 | V10 監査、検知及び対応 | どのように記録し、発見し、被害を食い止めるか |

### 6.2 レベル

| レベル | 位置づけ | 適合するプラットフォーム |
| --- | --- | --- |
| L1 | 基礎。欠如すると越権、資格情報の漏えい又は責任追及ができない状態が直接生じる | 企業内で利用するすべてのエージェントプラットフォーム |
| L2 | 標準。主流の企業セキュリティレビューで求められる機能 | 内部データを扱い、複数の業務システムに接続するプラットフォーム |
| L3 | 強化。多層防御及び精緻なガバナンス | 金融、医療、重要インフラなどの規制の厳しい業界、又は機微性の高いデータを扱うプラットフォーム |

判定規則：次のいずれかを満たすものは L1 に分類する。第一に、欠如した場合に、外部攻撃者、権限を逸脱した内部ユーザー又はチャネルのなりすまし者（TA1、TA2、TA6）が、他の条件なしに越権又は資格情報の取得を行えるもの。第二に、欠如した場合に、制御を失ったエージェント、悪意あるサプライチェーン構成要素又はプラットフォーム内部の関係者（TA3、TA4、TA5）が、資格情報の平文、又はユーザー間若しくはテナント間を横断するデータを直接取得できるもの。第三に、欠如した場合に、1回の操作の要求元ユーザー、実行エージェント、委任チェーン又は承認者を特定できないもの。他の条件と組み合わせなければ悪用できないもの、又は主として影響範囲を狭めることを目的とするものは L2 に分類する。特定の高リスクシナリオを対象とするもの、又は大きな投資を要するものは L3 に分類する。L1 の要件は、L2 及び L3 の要件を実装の前提としない。

本版は全 240 件の要件を含み、62 の節に分布する。内訳は、L1 が 90 件、L2 はこれに加えて 137 件、L3 はさらに 13 件を加える。L1 は、欠如すると直接悪用されるか、又は責任追及ができない状態を引き起こす統制のみを残している。他の L1 要件と重複する実装の詳細、アラート、多層防御及び管理手続は L2 に配置する。

### 6.3 適用条件

一部の節は、プラットフォームが特定の機能を備える場合にのみ適用される。節の冒頭に明記する。例：「本節は、オフライン委任タスクをサポートするプラットフォームに適用する」。プラットフォームがその機能を備えない場合は、節全体を「不適用」と記録し、適合率の算定対象に含めない。

### 6.4 規範用語と番号

- 要件はすべて「〜すること」の形で記述する（原文の「应」に相当する）。必須かどうかはレベル及び適用条件によって決まる。説明文中の「宜」（推奨の意）は要件を構成しない。
- 番号の形式は「V章.節.条」とする。例：V4.1.3。条項を削除した後も番号は再利用せず、新規の条項は節の末尾に追加する。
- 各要件は検証可能な結果を1つ記述する。要件が複数の文から成る場合は、すべてを満たしたときに限り満たしたと判定する。
- 「〜できること」「〜をサポートすること」と記述された要件は、プラットフォームがその機能を備え、かつ企業が有効化できることを判定する。その他の要件は、評価対象の配備において有効化され、機能していることを判定する。サプライヤー評価では前者のみを判定し、セキュリティレビューでは両方を判定する。
- 要件がプラットフォーム以外のシステム（下流システム、内部ネットワークのサービス、従業員端末など）を対象とする場合は、利用企業が実施を担い、評価時に責任主体を個別に記録する。
- 要件に数値が示されていない期限、周期及び閾値（「短期間有効」「定期的に」「合意された期間」など）は、企業又はプラットフォームが具体的な数値を書面で定め、設定において有効化されているものと判定する。下表は推奨する既定値であり、企業はリスクに応じて調整してよい。

| 項目 | 関連要件 | 推奨既定値 |
| --- | --- | --- |
| 下流アクセストークンの有効期間 | V1.3.4、V4.6.1 | 1時間以内 |

## 8、V2 委任と実効権限

エージェントの権限の上限は、エージェントが代表する人に由来するものであり、プラットフォーム自身が保持する資格情報に由来するものではない。実効権限は3.14に従って積集合をとり、委任チェーンに沿ってのみ狭めることができる。

## 10、V4 資格情報と出口での実行
