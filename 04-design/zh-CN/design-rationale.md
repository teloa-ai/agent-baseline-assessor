# 从 Teloa 开发到智能体安全基线：设计思考

作者：Max Luo · 发起与维护：[Teloa AI Security](https://github.com/teloa-ai) · 2026-10-11

**简体中文** · [English](../en/design-rationale.md) · [返回项目首页](../../README.md)

本文以 [CC BY 4.0](../../LICENSE-DOCS) 许可发布。

这份基线来自 Teloa 开发中反复出现的问题：AI 同事获得了工具后，以谁的身份执行？一个人批准的权限能否被转交给其他 Agent？在群里交办任务，会不会把个人数据带给其他成员？凭据加密保存后，执行过程是否仍可能泄露？

这些问题不能只靠模型遵守提示词来解决。平台需要在可信组件中检查身份、权限、调用参数和接收方，并让拒绝、撤销和审计真正生效。本项目结合公开规范，把这些设计问题归纳成可验证要求，供其他企业智能体平台使用和评审。

以下场景说明设计推导与核验方法，不是已发生事故的记录，也不是 Teloa 的达标报告。要求以[基线正文](../../01-standard/zh-CN/baseline-v1.0.md)为准；具体产品能力以相应版本、部署配置和验证证据为准。

## 1、从最小权限到最小自主

传统权限控制回答「能访问什么」。Agent 还需要回答「能自行决定什么、代表谁行动、能持续多久」。用户有权删除文件，不代表他委托整理目录时也批准了批量删除；能读取一个账户，不代表能把结果发到群里。

因此，本基线用最小自主作为总纲，并分别约束资源权限、任务范围、操作风险、审批、委托与输出。最小自主的术语来源与外部规范映射在正文中注明；本项目补充的是围绕企业身份与授权的具体控制要求。

## 2、五个代表性设计问题

### 2.1 工具已配置，不等于每次调用都获授权

**问题。** 管理员给某个 AI 同事配置了连接器，这只是能力上限。用户本人可能没有全部资源的权限，当次任务也可能只需要其中一部分。子 Agent 如果继承完整连接器权限，会扩大原始委托。

**设计选择。** 每次调用时在可信组件中计算有效权限：代表用户访问时，取用户当前权限、Agent 授权范围与任务声明范围的交集；下游 Agent 还受上游委托范围限制。工具清单过滤用于减少误调用，执行时的检查负责阻断越权。

**对应要求。** V2.2.1、V2.2.3、V2.2.5、V2.4.1、V3.2.1。

**怎样核验。** 用只有读取权限的用户发起任务，尝试写入；再让任务派生子 Agent，尝试扩大资源范围；执行过程中撤销用户权限后再次调用。每次都应被执行组件拒绝，并能追溯到用户、Agent 与任务。

**实践线索。** Teloa 的[安全模型概述](https://github.com/teloa-ai/teloa/blob/main/SECURITY.md#安全模型概述)说明了岗位工具授权的控制位置。复核时仍需检查实际调用路径是否全部经过该控制。

### 2.2 人批准的是具体操作，审批必须绑定真实参数

**问题。** 模型生成的「发送汇总邮件」摘要可能漏掉接收人、附件或批量范围。用户确认摘要后，如果执行参数发生变化，确认的对象与实际动作就不同了。

**设计选择。** 由平台从真实参数生成审批内容；执行时再次校验参数与已批准内容一致。为审批设置有效期，并限制重复请求。事先批准的计划必须明确工具、资源范围和上限。

**对应要求。** V3.4.1 至 V3.4.6。

**怎样核验。** 批准发送后替换收件人或附件，批准删除后扩大范围，重放过期审批，持续制造重复确认请求。验证变化或过期的操作被拒绝，原批准不会被挪作其他用途。

**实践线索。** Teloa 的[安全模型概述](https://github.com/teloa-ai/teloa/blob/main/SECURITY.md#安全模型概述)记录了外部副作用动作的审批流程。流程名称本身不能证明参数绑定、超时与重放控制已满足，仍需对应测试证据。

### 2.3 静态加密之外，还要控制凭据使用路径

**问题。** 密钥加密保存在磁盘上，只保护一种暴露方式。如果真实密钥进入上下文、环境变量、执行文件或工具回包，Agent 仍可能读取或外传。即使只能由宿主代发请求，获准的服务也可能回显密钥。

**设计选择。** 平台托管凭据，在受控出口按目标注入；同时校验目标、阻断旁路出口，处理回包和日志中的凭据。加密、按值脱敏和命令守卫分别提供保护，不能用其中一项替代整条访问路径的控制。

**对应要求。** V4.1.1、V4.1.2、V4.1.5、V4.2.1 至 V4.2.3、V4.7.1。

**怎样核验。** 尝试从上下文、执行环境和日志读取真实密钥；改写目标域名或路径；通过其他网络工具直连；模拟服务回显凭据。确认拒绝和剔除发生在执行环境收到秘密之前，并记录未覆盖的编码、渠道和第三方行为。

**实践线索。** Teloa 的[凭据存储与恢复](https://github.com/teloa-ai/teloa/blob/main/SECURITY.md#凭据存储与恢复)区分了存储保护、受控使用与残余风险。列为开发中或未发布的能力，不能直接作为已交付证据。

### 2.4 读取权限和输出可见范围必须分开检查

**问题。** AI 同事被允许读取个人账户资料，随后在多人群聊里接到相关任务。查询可能合法，但结果中的数据未必允许所有群成员查看。只读请求也能造成数据泄露。

**设计选择。** 读取时按发起者与任务权限授权；回复、共享和转交时，再按接收方权限检查。多人渠道只展示所有在场成员都有权访问的数据，超出范围的结果按正文要求转入私密渠道。记忆、上下文与产出物也保留权限和来源信息。

**对应要求。** V7.1.1、V7.1.2、V7.1.4、V7.2.2、V7.3.1、V8.3.1、V8.5.2。

**怎样核验。** 让两名权限不同的成员参与群任务，验证个人数据不出现在共享回复、历史记录和共享产出物中；再测试成员加入、会话转交、记忆检索与产出物分享。

**实践线索。** Teloa 的[凭据存储与恢复](https://github.com/teloa-ai/teloa/blob/main/SECURITY.md#凭据存储与恢复)记录了群任务与个人账户授权之间的风险。这类已知边界是提出要求的依据，不能用作已满足要求的证明。

### 2.5 应用守卫和执行隔离承担不同职责

**问题。** 拦截已知命令与路径，无法覆盖所有解释器、符号链接、编码或组合调用。如果执行环境能修改策略或读取宿主凭据，一条守卫规则的失效就可能绕过整个边界。

**设计选择。** 先按部署形态确定可信与不可信组件，再使用系统级隔离、默认拒绝的网络出口和 Agent 不能改写的策略执行点。守卫与脱敏用于纵深防御；隔离强度与旁路能力必须单独验证。

**对应要求。** V3.2.2、V3.2.3、V4.2.2、V5.1.2、V5.1.4、V5.4.1 至 V5.4.4。

**怎样核验。** 从执行环境尝试访问宿主凭据、其他会话和内网服务；尝试修改策略及放宽权限模式。复核哪些设置能被 Agent 改变、哪些只能由用户或管理员改变，并记录这些变化对评估范围的影响。

**实践线索。** Teloa 的[安全模型概述](https://github.com/teloa-ai/teloa/blob/main/SECURITY.md#安全模型概述)披露了部署默认值与会话级权限配置之间的边界。固定默认配置本身不能证明存在系统级隔离。

## 3、通用要求与具体部署之间的边界

基线以企业身份与授权为范围，参考架构见[正文第 4 章](../../01-standard/zh-CN/baseline-v1.0.md)。企业 IdP、策略决策点、出口网关和审计等组件各自承担明确职责；单用户本地工具、多用户企业平台和端侧 Agent 的信任假设不同。

评估前应写清产品版本、部署形态、启用能力、外部系统与责任方，再按正文的小节适用条件判断。缺失一项应有的安全控制不能简单标成不适用。对要求的架构约束或等效实现有异议时，应提出可验证的改进建议；本文不替代正文，也不授予条款豁免。

## 4、把设计目标变成可复核的评估证据

| 要记录什么 | 用途 |
| --- | --- |
| 要求编号与基线版本 | 明确依据，防止版本混用 |
| 产品版本、部署范围与配置 | 区分产品具备能力和当前部署实际生效 |
| 实现位置与测试记录 | 说明控制由谁执行，以及拒绝路径是否有效 |
| 满足状态、差距、责任人与计划 | 支持复核与后续改进 |
| 未覆盖路径与残余风险 | 限定结论的实际适用范围 |

源码位置、功能演示和单次测试都只是证据的一部分。自评工具负责记录与汇总，不会自动验证实现，也不产生独立认证。示例报告、覆盖矩阵和可导入的模拟数据见[评估示例](../../02-usage/zh-CN/usage.md#评估示例)。
